How agents learn

How agents learn • Three layers of context: lessons live per agent on SER; project knowledge lives in the project’s repository AGENTS.md or design/ notes, changed through a pull request; run history lives on SER and includes reports, answers and outcomes. • Every run receives, in order: the job (What it does); lessons that apply to this project; the project’s AGENTS.md; the last report; recent outcomes of its own proposals (merged / closed + optional reason / changes asked / edits before merge as a diffstat). Preserve source links and project identity. • Record outcomes for every proposal and pull request the agent brings. Reasons are optional. Owner answers include Close with a reason, Ask for changes, edits before merging, Stop suggesting this, and explicit chat instructions. • Nothing inferred is kept without the owner’s Keep it. Inferred patterns bring a Learning proposal with evidence and a before/after instruction diff. Edit changes the proposal and returns to Keep it; Save in that editor does not keep it. Close frees its slot without adding a lesson. Learning reserves a proposal slot like any other and does not consume a project PR budget. • Explicit instructions save immediately with a visible, undoable receipt: “Learned: Keep pull requests under about 100 lines · Edit · Undo”. Teaching the job remains What it does; learned preferences belong in What it’s learned. An explicit project convention still goes through the project-knowledge PR flow. • Every lesson shows its source. Source links open the original answer, PR or chat message. The owner can edit or remove any lesson, and choose All projects or Chosen projects. LessonEdit shows one existing lesson; #explicit shows its chat source; #proposal edits an inferred proposal before Keep it. Other lesson links carry agent and lesson identity to the same editor layout. Changes affect future runs; removal and Keep it have Undo. • At most 20 lessons per agent. The limit stops only lessons it worked out itself: what you tell it directly always saves, even past 20. Over the limit, it brings a Learning proposal that combines lessons and waits for Keep it; it never silently deletes or combines lessons. Do not claim “Learned” until storage succeeds. Lessons never grant access or widen approval rules; selected scope intersects current access. • Project facts, such as tally’s lowercase header and buttons, are Improvement proposals with a ready AGENTS.md diff and PR. Merge / Ask for changes / Close follow the normal care flow. Owner preferences remain per agent, not in the repository. Design/ knowledge follows design approval rules as well. • Server work needed: a lesson store with text, project scope and linked sources; outcome records for proposals and PRs; Learning proposal kind; prompt assembly in the order above; project-knowledge PRs through the normal care flow; idempotent answers and undo receipts. Keep suppressions distinct from inferred lessons: Stop suggesting this takes effect immediately for that finding, but any broader inferred lesson needs Keep it. • New-agent details show “Nothing learned yet. It learns from how you answer its work.” Existing shared details show lessons between What it does and Looks after. Reports and weekly summaries only claim a lesson after it was saved or kept. • Review widths: web 1440 and 700, iPhone 390. Owner renders and commits; this change is design only. • Prototype states are navigable with fragments: ProposalLearning#kept and #undone; AgentLearned#undone; LessonEdit#proposal and #explicit; ProposalFix#closed-too-big (and each other reason). The editor’s typed value and selected projects are illustrative static fields; the implementation must carry draft edits back into the proposal diff before Keep it. Saving an existing lesson or removing one never changes the job text.

Design: how it works

Design: how it works • Designs live in the repo in design/: canvas.json plus one HTML file per board, built from the design system. Every element has a stable layer ID (data-layer). • Layout follows Figma: navigation on the left (the d menu with Waiting on you, Designs and the branch, File | Assets, Pages = sections, Layers), the full properties panel on the right, the tool bar at the bottom with vector tools. • Edits save to a design branch; main changes only through Propose for review and approval (Design tab, chat card, Waiting on you). • Agents edit through design tools (read, render, structured edits, presence, comments, propose), each on its own branch, shown as a live overlay you accept or discard. • iPad uses the desktop layout; iPhone has the full canvas with Layers and Edit as sheets. Build order: 1. Canvas, Layers, Comments, review, and Ask an agent with live editing. 2. Direct edits: text, properties and tokens. 3. Vector tools and Assets.
