## 2. Who depends on whom

## 5. The target shape

**Proposal:** one composition root, one small kernel API, and feature modules. Keep the edge and worker process isolation. “One server” means one set of ownership rules, not one operating-system process or one enormous SQLite file.

```text
server/main/           boot, listeners, supervisor wiring, dependency injection
server/kernel/         db, events, auth, jobs, computers, files, process, HTTP
server/features/       repositories, tasks, agents, decisions, design,
                       packages, observability, backups, updates, releases, catalog
server/transports/     v2, workspace-compat, engine-compat, Git, npm, worker, WebSocket
shared/                existing public client contracts
```

This is a proposed destination, not directories that already exist. Keep public URLs and `shared/v2` contracts stable while internals move.

A file belongs in the kernel only when its rule is independent of task, release, package, design or inbox meaning. A lease primitive qualifies; “retry this deployment after 20 minutes” does not. A blob writer qualifies; “which checkpoint belongs in a task review” does not. Schema migration mechanics qualify; the release schema does not.

Features import kernel interfaces and their own internals. They do not import sibling feature implementations. Main wires narrow ports such as `RepositorySource.readCommit`, `DecisionSink.request`, `ReleaseCommands.request`, `RuntimeHealth.read`, and `BackupProvider.capture`. Port types sit in dependency-free contracts; the composition root supplies implementations. This replaces today's `live → releases-api`, `workspace → v2/design` and `pipeline → ci-releases` imports without creating another catch-all service locator.

The release engine ends up in `features/releases/engine/`: graph compiler/planner, Docker adapter, runtime store, volume/provider operations, local/remote execution and activation. Product release policy, Watch, rollback and journals sit beside it behind one `ReleaseService`. Upload, CI, pipeline, Catalog and v2 handlers are callers. The edge consumes routing snapshots; it does not call release policy. Keep the existing reservation, activation receipt, encrypted journal, and crash-recovery semantics while moving ownership (`v2/releases*.ts`, `application-graph-executor.ts`, `graph-runtime-store.ts`, `ci-releases.ts`, `edge/routes.ts`).

Backups retain separate providers for app data, Home bundle, workspace offline snapshot and whole-directory copy. Computers retain distinct execution-agent and task-worker credentials. These are deliberate boundaries, not duplication to erase.

Each numbered row is a releasable change. For repeated moves, ship one named feature at a time. Keep compatibility re-exports until callers move. Never rename records, IDs, database files, encryption addresses or canonical manifests just because code moves.
