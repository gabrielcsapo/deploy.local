# Task workers and provider connections

Use **Settings → Providers** (`/dashboard/settings#settings-providers`) to start the coordinator's task worker and configure the providers used on that computer. Computers → Task computers links to the same settings. An online deployment runtime does not substitute for a task worker.

The managed task worker runs as the ordinary operator named by the installed updater's root-owned configuration on Linux. It connects to the coordinator through the authenticated worker API, using an owner-scoped credential. It never opens the root-owned workspace database or changes its permissions. The control plane supervises the process, restarts it after a failure and resumes enabled workers after an application restart. Its files live under the operator's `~/.local/share/deploy.local/task-workers/` directory. Other manually started workers and candidate databases are separate.

Codex can use its worker account or a key entered in the app. The managed worker uses a private `CODEX_HOME`; initial account authentication can be adopted from the operator's existing CLI authentication cache without importing desktop configuration. **Sign in with ChatGPT** starts the supported device flow and displays the provider link and one-time code in the owner's settings. The user completes authentication on the provider's page. Codex keeps its refreshed authentication cache privately on the worker. [Official authentication documentation](https://developers.openai.com/codex/auth/).

Claude can use the worker's existing Claude account or an Anthropic API key entered in the app. Local and compatible APIs accept a base URL, explicit model, local/API billing mode and an optional key. HTTP is accepted only for loopback inference; remote endpoints require HTTPS. Connection keys are encrypted with the existing application secret-store key, bound to owner, worker and provider. Browser reads return only key presence. Worker credentials cannot read another worker's settings, and run children receive only their selected provider's configured environment.

Changes apply before the worker's next run rather than changing a running agent's credentials. The settings display the worker's applied revision, actual account sign-in state, missing runtimes and application errors. “Configured” for key-based connections means the worker applied the configuration; it does not assert that the provider has accepted a billable inference request. The composer uses the selected worker's capabilities and model catalog, rather than the root server's PATH.

The repository service remains a separate supervisor child for Git storage/import and checkout preparation. There is exactly one entry for each service. Git operations do not start coding agents, and task execution stays in its assigned worker checkout.
